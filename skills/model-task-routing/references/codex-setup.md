# Codex 安装、配置与更新

共享调度技能的版本见 `model-task-routing/SKILL.md` 的 `metadata.version`。本版在通用职责之外提供可采用的模型与档位示例：主要判断、主力实现、有界辅助分别配置。推荐值只维护在仓库 `examples/agents-config.toml` 与 `examples/agents/*.toml`；这些文件不会自动安装、改写配置或授予权限。

## 先核对接收端

采用示例前，核对当前客户端支持的配置字段、自己的账号/工作区可用模型与思考档位，以及项目或专项的更严格限制。示例型号不可用时说明缺口，由使用者决定适用替代方案，不静默降档或把未核实的值写入配置。推荐分工不证明质量改善、速度提升或费用节省；试运行仍遵守原费用授权。

按实际 `CODEX_HOME` 找到用户级配置，未设置时默认 `~/.codex`。技能目录由客户端发现规则决定：官方列出用户级 `~/.agents/skills`、仓库级 `.agents/skills` 和机器级 `/etc/codex/skills`，不能只凭 `CODEX_HOME` 推断技能位置。项目级 `.codex/config.toml` 还需遵循项目加载和信任规则。

把两个完整技能目录 `model-task-routing` 与 `landing-execution` 放在同一个实际技能发现目录中，保持同级位置和附属文件。`landing-execution` 使用 `../model-task-routing/SKILL.md`，不能只装其中一个。仓库根的 `examples/` 是配置参考；安装技能目录不会自动安装这些角色。

## 逐字段合并默认值与角色

先备份实际生效的 `config.toml`、已有角色定义和待更新技能目录；比较同名文件及接收端改动，只合并本次需要的值与职责。不要用样例替换整份配置，不覆盖账号、provider、权限、项目路径、并发上限或已有角色的其它设置。

`examples/agents-config.toml` 是配置示例片段，含三种位置：

- 主对话默认 `model` 和 `model_reasoning_effort` 属于 **config.toml 顶层**，必须放在任何 `[section]` 前。不要贴在文件末尾的某个角色或provider小节里。
- 通用子任务兜底 `default_subagent_model` 和 `default_subagent_reasoning_effort` 属于 **`[agents]`**。已有此小节时只合并字段，不重复声明。保留已确认的并发及其它设置。
- 专用角色通过 **`[agents.<role>]`** 的 `description` 和 `config_file` 接入；对应角色文件中的模型与档位明确覆盖该角色。先核对当前客户端是否已发现或注册该角色，不重复登记同一角色。

官方支持用户级 `~/.codex/agents/` 或项目级 `.codex/agents/` 下的自定义角色文件；角色身份由必需的 `name` 字段确定，另需 `description`、`developer_instructions`。文件名相同只是维护约定。接收端若通过 `config_file` 加载角色层，按该方式接入；文件已复制不代表客户端已加载。

相对 `config_file` 路径以**声明它的配置文件**为基准。仓库示例的 `agents/lead.toml` 相对 `examples/agents-config.toml`；合并到目标配置后，把职责文件放在该配置旁的 `agents/` 目录，或相应调整路径。搬到项目配置时重新核对路径，不假设原路径仍有效。

示例提供十个现有专用角色，只登记实际需要且没有合适原生入口的角色。官方内建 `default`、`worker` 可继续作通用兼容入口，无需另建同义角色文件；核对它们是否使用期望的 `[agents]` 兜底，而不是继承旧的辅助默认。已有专用覆盖或工具绑定时分别核对，不能仅靠角色名认定模型。

自定义同名 `explorer` 会优先于内建角色；想保留原生入口时省略其登记和职责文件，并核对实际绑定。`explorer` 只负责只读事实辅助，素材角色只按已批准方向产出，不负责需求或视觉方向判断；未定选择交回判断角色。

## 更新已安装的旧版

1. 从仓库新提交获取文件。已有克隆先保留自己的改动，再用 `git pull --ff-only` 更新发布分支；有冲突时比较合并，不用强制覆盖。下载包同样先解压到另一个目录比较。
2. 核对两个技能的版本与现有差异，更新需要的正文和附属文件，保留本地已确认约束。本版职责变化位于路由技能；落地技能无变化时无需重复覆盖。
3. 同时对照新的主/子默认示例与所用角色TOML，逐字段合并模型、档位和必要职责。旧示例未填模型时，仅更新技能正文不会自动得到本版配置。
4. 在目标客户端按其要求重新加载或开启新会话，然后做下面的核验。出现问题时按保存的原件或上一提交恢复本次差异，保留之后的新改动，不重写共享历史。

## 核验配置与首次使用

先解析配置/角色TOML，确认主默认处于顶层、子默认处于 `[agents]`，所有启用的 `config_file` 都存在，两个技能互相引用完整。核对账号支持的型号/档位与配置一致，保留权限、费用、并发及项目约束。不能用“语法能解析”证明型号对该账号可用。

新文件不会切换已运行会话。首次新派遣前检查工具原生角色绑定；与配置不符或未知时，只有工具允许显式覆盖才传入已核实的模型/档位并携带该职责，不支持时说明缺口。提示词写角色名不能切换模型。显式派遣值可覆盖 `[agents]` 默认，其它继承按接收端实际规则核对。

在既有授权和费用边界内做一次低影响派遣，查看返回的实际角色、有效模型/档位和可用工具；运行元数据不可见时标为未知。示例、解析、复制和重新加载都不能替代这项运行证据，也不能冒称同事机器已生效。并发依据当前工具真实容量、整棵任务树占用和专项上限；不因示例增加权限、费用额度、项目访问或外发授权。
